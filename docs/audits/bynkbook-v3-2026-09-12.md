## Plaid compatibility and safeguards

Plaid SDK, Prisma client/adapter, SST version, credentials, account mappings, production endpoints, webhook infrastructure, and the documented live infrastructure bridge were not switched. The existing distinction between routine sync and explicitly requested balance/transaction refresh is preserved.

The frontend now shares a retryable SDK loader with a 15-second deadline, checks that Link actually loaded, and cleans up Link handlers when account/business context changes. Reconcile and Operations propagate cancellation through sync requests and monitors. A response marked pending, draining, or having more pages is not presented as a completed sync. Failed or missing confirmation payloads are errors. Late status responses cannot update a newly selected Reconcile account. An uncertain refresh no longer claims that no transaction changes occurred.

## Verification

- 87 frontend tests and 383 backend tests pass: 470 total.
- Frontend production build, lint, backend infrastructure typecheck, function typecheck, and Prisma schema validation pass.
- Public browser suite against the production build: 9 pass, 1 intentionally skipped because its pointer-size check applies only to mobile.
- 14 authenticated default routes inspected at 390, 768, and 1440 pixels. No page-level horizontal overflow or unexpected failed API reads. The audit guard deliberately blocks the automatic category-suggestions POST; that feature was not exercised against production.
- Focused browser checks cover mobile paging, incremental loading, entry inspection, failed-save recovery, search result navigation, receipt cancellation, keyboard navigation, dark theme, and simulated Plaid opening review.
- Both frontend and backend production dependency scans report zero advisories. The frontend full scan is also clean. Backend full scan retains two low-severity tooling findings from SST's AWS SDK v2 dependency; there are no moderate/high/critical findings. The suggested removal requires an SST major upgrade, which is outside this banking-sensitive patch.

Evidence: [V3 screenshots and JSON results](../../output/playwright/bynkbook-v3-2026-09-12/). Timings are local browser/network observations, not production p95 measurements or proof of a percentage speedup. Database pool budgets need realistic concurrency testing before rollout.

## Remaining release work

1. Deploy compatible backend and frontend changes through the established release process. Direct search lookups, setup facts, read policies, Operations completeness, and pool budgets require the new backend. No schema migration was introduced here.
2. Run a staging banking matrix with authorized test accounts: new/existing account connect, OAuth return, reconnect, multiple accounts, pending-to-posted, duplicate/removal events, opening choices, manual refresh, webhook-to-worker, and disconnect. Record account balances and audit history before and after.
3. Validate the full custom-role read matrix across alternate APIs, including exports, activity, summaries, and standalone invoice endpoints. The seven protected read surfaces above are an improvement, not a complete assertion about every endpoint.
4. Measure large-ledger behavior, query plans, slow-device interaction latency, and total Lambda/database connection demand. Splitting lightweight bank health from analytics and adding production field measurements remain follow-ups.
5. Verify backup restore, alert delivery, error-rate monitoring, Google sign-in/MFA, and approved Privacy/Terms content. These require operational evidence or product decisions that local tests cannot provide.

The code changes reduce specific unnecessary work and remove concrete usability defects. Broader navigation consolidation, complete monolith extraction, screen-reader/zoom testing across every workflow, and the operational items above remain explicitly open.
